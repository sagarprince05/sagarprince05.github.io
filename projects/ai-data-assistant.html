AI Data Assistant (Slack Bot)

A chat assistant that lets a non-technical team ask questions about live operational data in plain English — including typos and mixed Hindi-English — and get an accurate, verified answer in about three seconds.

The problem

Operational data sat in a database only technical people could query, so everyone else had to ask around and wait. The goal was instant self-serve answers in the tool the team already used, with a hard rule that the assistant must never invent data — and no budget for infrastructure.

What I built

  • Natural language → SQL. An LLM converts each question into a read-only query, guided by a hand-written data dictionary that captures the schema's quirks and the team's vocabulary.
  • Anti-hallucination design. Answers come only from real query results, and every reply carries a receipt of what was searched. Single-value answers bypass the language model entirely so a number can never be garbled. If the database is unreachable, the assistant says so instead of guessing.
  • Resilience on free tiers. A fallback chain across multiple models plus a queue for burst traffic kept it answering when any one model hit a rate limit — including when a provider retired two models without notice.
  • Security by design. Request signature verification, an admin-managed allowlist, and a dedicated read-only database role scoped to a single schema with a statement timeout, so the assistant cannot modify or reach data outside its scope.
  • Self-updating. A scheduled job refreshes the assistant's picture of the schema automatically, so new data appears without a redeploy. Admins can also teach it new terms from chat.

Engineering challenges

  • Direct database connections from edge functions hit platform subrequest limits — solved with a connection-pooling layer after diagnosing a double-pooling conflict.
  • Early versions could produce a confident answer when the data path failed; I replaced that with layered guards that fail honestly and show their working.
  • Timezone handling and messy free-text data produced wrong answers until I captured each case as a rule in a living data dictionary.
